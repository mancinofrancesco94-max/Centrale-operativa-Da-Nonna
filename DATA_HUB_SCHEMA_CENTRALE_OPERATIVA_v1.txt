# Centrale Operativa — Data Hub v1
## Specifica dati per Claude Code

## Obiettivo
Costruire un Data Hub PostgreSQL/Supabase multi-azienda e multi-sede, riutilizzabile per business diversi. Da Nonna è il primo tenant e il primo verticale ristorazione.

## 1. Principi obbligatori

1. PostgreSQL come database.
2. Multi-tenant: `organization_id` su tutte le entità aziendali e `location_id` dove il dato è riferibile a una sede.
3. Separare gli schemi PostgreSQL: `raw`, `core`, `restaurant`, `finance`, `workforce`, `crm`, `marketing`, `analytics`, `ops`.
4. Conservare sempre il dato originale ricevuto dalle API.
5. Mai sovrascrivere il dato fiscale originale.
6. Per le vendite conservare separatamente `fiscal_date`, `management_date`, timestamp reali e `service_period`.
7. Tutte le KPI gestionali usano `management_date`.
8. Tutte le integrazioni devono essere idempotenti.
9. Ogni record importato conserva `source_system_id`, `external_id`, `source_updated_at` se disponibile.
10. Timestamp in `timestamptz`; storage UTC; timezone della sede configurabile.
11. Denaro in `numeric(14,2)` e quantità in `numeric(14,4)`; mai `float` per valori economici.
12. Tutte le modifiche allo schema via migrations versionate in Git.
13. Ogni tabella principale ha `created_at` e `updated_at`.
14. UUID come PK di default.
15. Struttura riutilizzabile anche per business non ristorativi.

## 2. Schemi PostgreSQL

```sql
create schema if not exists raw;
create schema if not exists core;
create schema if not exists restaurant;
create schema if not exists finance;
create schema if not exists workforce;
create schema if not exists crm;
create schema if not exists marketing;
create schema if not exists analytics;
create schema if not exists ops;
```

## 14. REGOLE GESTIONALI CONFIGURABILI

### `core.management_rules`
Non hardcodare nel frontend le regole importanti.
- id uuid PK
- organization_id uuid FK
- location_id uuid nullable
- rule_type text
- rule_key text
- config jsonb
- valid_from date
- valid_to date nullable
- active boolean
- created_at
- updated_at

Esempi: operational_day_cutoff, service_periods, weekly_close_day, weekly_close_time, target_food_cost_pct, target_labor_pct, target_mol_pct, bep_rules.

Esempio `service_periods`:
```json
{
  "breakfast": {"from": "08:30", "to": "12:29"},
  "lunch": {"from": "12:30", "to": "15:00"},
  "afternoon": {"from": "15:01", "to": "18:29"},
  "dinner": {"from": "18:30", "to": "23:59"},
  "late_service": {"from": "00:00", "to": "03:00", "management_day": "previous"}
}
```

Regola: `management_date` deve essere calcolata lato backend/database service, non solo nel frontend. Il cutoff è fallback: se NetFood espone sessione cassa/apertura ordine/identificatore servizio, usare quello come fonte primaria.
